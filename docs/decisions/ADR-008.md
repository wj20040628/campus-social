# ADR-008: 对外 API 契约统一 /api/v1 前缀，由 Nginx 做版本路由

## Status

Accepted (2026-10-08) —— 标记为**带已知缺陷的折中方案**，见 Consequences

## Background

### 现状（磁盘实测）

- 后端 Controller 无任何版本前缀：`@RequestMapping("/auth")`、`/post`、`/chat` ...（12 个 Controller 全部如此）
- Nginx 反代时剥掉 `/api`：`rewrite ^/api/(.*)$ /$1 break;`（`frontend/nginx.conf`）
- 前端 `VITE_API_BASE_URL` 默认 `/api`
- 即：对外 URL 是 `https://domain/api/auth/login`，内部路由是 `/auth/login`

### 团队规范

架构规范要求：所有端点必须包含版本号前缀 `/api/v1/`；版本号体现在 URL 路径中（显式优于隐式）；后续不兼容变更新增 `/api/v2/`，v1 保持兼容至少 6 个月。

### 冲突

现状无版本段。改后端所有 Controller 的 `@RequestMapping` 加 `/v1` 会牵动 12 个 Controller、前端 request 封装、WS 端点（`/ws/chat` 不应加版本前缀，它是协议端点不是 REST 资源）、拦截器 exclude 路径、Swagger 配置 —— MVP 阶段改动面过大且风险高。

## Decision

**对外契约统一为 `/api/v1/*`，由 Nginx 在接入层做版本路由，后端内部路由保持现状不加前缀。**

```nginx
# frontend/nginx.conf —— 修改 /api/ 段为 /api/v1/
location /api/v1/ {
    rewrite ^/api/v1/(.*)$ /$1 break;
    proxy_pass http://127.0.0.1:8080;
    ...
}
```

前端 `VITE_API_BASE_URL` 改为 `/api/v1`。

后续若需不兼容变更：
- 方案一（推荐）：后端 Controller 真正拆出 `/v1` / `/v2` 两套路由，Nginx 分别路由
- 方案二（届时评估）：后端新版本服务独立端口，Nginx 按 `/api/v2/` 转发

## Consequences

**正面**
- 对外契约带版本，满足规范要求，前端/第三方感知到的 URL 是版本化的
- **零后端改动**：12 个 Controller 一行不动，回归风险为零
- WS 端点 `/ws/chat` 不受影响（它本来就不走 `/api` 前缀）
- 拦截器 `excludePathPatterns`、`springdoc` 配置全部不动

**负面 —— 这是一个不完美的方案，必须说清**

1. **版本是"表面的"**。后端内部路由仍是 `/auth/login`，代码里看不到版本概念。这意味着：当 `/api/v2` 真正需要时，**Nginx 无法凭空造出 v2 的行为**，仍然要改后端。本方案只解决了"对外 URL 好看且预留了空间"，没有解决"多版本共存"这个根本问题。
2. **内部与外部路径不一致**，排查问题时需要在脑子里做一次映射，长期是认知负担。
3. **Swagger 文档输出的路径是 `/auth/login`**（内部路径），与实际对外 URL 不一致，需要人工说明，否则前端照着 Swagger 联调会 404。

**若这个不一致不可接受，替代方案是**：全局给后端加 `server.servlet.context-path: /api/v1`，同时把 WS 端点和拦截器路径整体调整。代价是一次全局改动 + 全量回归（约 0.5–1 人日）。**MVP 阶段不做，登记为 D2 技术债 TD-03 的升级选项。**

**强制要求**
- 前端所有请求必须走 `VITE_API_BASE_URL`（当前默认 `/api`，改为 `/api/v1`），**禁止在代码里硬编码 `/api/xxx` 路径**
- `openapi.yaml`（Phase 2 交付）里所有 path 必须写成 `/api/v1/...`，与对外契约一致
- 在 `nginx.conf` 顶部注释说明"内部路由无版本前缀，版本由本文件统一映射"，防止后人困惑
