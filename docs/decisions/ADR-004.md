# ADR-004: WebSocket 保持单机内存广播，不引入消息队列；临界点为 5000 在线连接或第 2 个实例

## Status

Accepted (2026-10-08)

## Background

现状：`WsSessionManager` 用 `ConcurrentHashMap<Long, Set<WebSocketSession>>` 在 JVM 内存里维护 userId → session 映射（`WsSessionManager.java:22-23`），`WsPushService` 直接本机广播。端点为 `/ws/chat` 与 `/ws/notify`（`WebSocketConfig.java:26-31`）。

问题：这个设计在单实例下正确，多实例下会出现"消息只推给连在 A 实例的用户，连在 B 实例的用户收不到"。

需要判断：在"单台云服务器、几百并发"的场景下，是否要现在就引入 Redis PubSub 或消息队列做跨实例广播。

## Decision

**MVP 保持单机内存广播，不引入 Redis PubSub，更不引入消息队列（RabbitMQ/RocketMQ/Kafka）。**

同时必须做的两件事：
1. 在 `WsPushService` 的 Javadoc 顶部写明"本机广播，部署第 2 个实例前必须改造为 Redis PubSub 广播"，防止未来横向扩容时静默踩坑（登记为 TD-20）
2. 把当前在线连接数暴露到 `/actuator/health`，作为临界点监控指标

### 容量测算依据

- 每个 WS 长连接服务端开销约 50–100KB（Socket 收发缓冲 + Session 对象 + 用户上下文）；**连接本身不独占线程**，这点是 WS 优于 HTTP 长轮询的关键
- Tomcat 默认 `maxConnections=8192`、`maxThreads=200`。NIO 模式下连接不占线程，但消息处理仍走线程池
- 2核4G 机器、JVM 堆 1.28G：理论 1.3 万–2 万连接，但 **CPU 会先于内存成为瓶颈**（心跳维持 + 上行报文处理 + 广播扇出）

### 明确的临界点（分档执行表）

| 阶段 | 同时在线 WS 连接 | 做法 | 工作量 |
|---|---|---|---|
| 阶段 0（MVP 上线） | < 1,000 | 现状不动 | 0 |
| 阶段 1 | 1,000 – 5,000 | 单机 + 参数调优：`server.tomcat.max-connections=10000`、`max-threads=400`、`ulimit -n 65535`、`net.core.somaxconn=65535`；开启 WS 心跳与死连接清理 | 0.5 人日 |
| **阶段 2（临界点）** | **> 5,000** 或 **实例数 ≥ 2** | **必须**引入 Redis PubSub：`WsPushService` 改为 `convertAndSend`，每实例订阅频道并只转发本机命中的 userId | 1 人日 |
| 阶段 3 | > 50,000 | 换 Netty/WebFlux，或拆独立 IM 服务 | 3–5 人日 |

**记住这两个触发条件，满足任一即升级：**
1. **峰值同时在线长连接 > 5,000**
2. **后端实例数 ≥ 2**（哪怕每实例只有 500 连接，内存 Session 也会导致跨实例消息丢失）

业务量换算：按校园场景同时在线率 15–25% 估算，**日活超过 2 万**才需要动这个。MVP 目标（本校几千人）远未触及。

## 为什么不选消息队列

| 方案 | 评估 |
|---|---|
| 内存广播（选） | 延迟最低、故障面最小、零组件。缺点：不可跨实例 |
| Redis PubSub（临界点后选） | 够用。Redis 已在栈里，零新增组件。缺点：无持久化，实例重启期间的消息会丢（对"在线推送"场景可接受，离线用户走未读数拉取） |
| RabbitMQ / RocketMQ | **过度设计**。为"在线时推一条提示"引入一个需要独立运维、有磁盘持久化、有消费者组语义的中间件，收益为负。**本 ADR 明确排除，任何阶段都不选** |

## Consequences

**正面**
- 零新增组件，MVP 阶段延迟最低（无 Redis 一跳）、故障面最小
- `WsPushService` 是唯一推送入口，改造点集中，将来改 PubSub 只需动这一个类
- 避免了"为不存在的问题建基础设施"

**负面（必须承认）**
- **多实例是硬墙**：一旦因为任何原因（性能、可用性）部署第 2 个实例，必须立刻改造，否则出现"一半用户收不到消息"的**沉默故障** —— 不报错、不崩溃、只是消息丢了
- 单机故障 = 全部 WS 断开
- 未来改造时若忘了这条约束，故障模式非常隐蔽（用户投诉"消息有时收不到"，而不是"系统挂了"）

**强制缓解措施**
1. `WsPushService` 类级 Javadoc 写明单机限制（TD-20）
2. `/actuator/health` 暴露 `ws.connections` 指标
3. 在部署文档顶部写明"扩到 2 个实例前，先做 ADR-004 阶段 2 改造"
