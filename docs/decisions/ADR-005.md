# ADR-005: 生产数据层锚定 MySQL 8.4 LTS + Redis 7；代码一律按 Redis 5.0 语义编写

## Status

Accepted (2026-10-08)

## Background

### 事实基线（磁盘实测，非假设）

| 组件 | 本地实测 | 声明/配置 | 问题 |
|---|---|---|---|
| MySQL Server | **9.0**（`F:\MySQL\MySQL Server 9.0`） | `README.md:69` 写"MySQL 8.x" | 9.0 是 Innovation 版，**EOL 2024-10-15**，已不再收到任何安全补丁 |
| Redis | **5.0.14.1**（`D:\Redis-x64-5.0.14.1`） | `README.md:70` 写"Redis 6+" | 声明与实际不符 |
| docker-compose | 无（本地跑不了） | `docker-compose.yml:14` `mysql:8.0`、`:36` `redis:7-alpine` | 与本地两个版本都不同，且从未被验证 |
| mysql-connector-j | **8.4.0** | 用户明确要求保持 | 与 8.4 LTS 服务端主版本对齐 |

### 已踩过的坑（团队记忆，必须写进约束）

`opsForValue().getAndDelete()` 在 Redis 5.0 上必抛 `ERR unknown command GETDEL`。原因：Spring Data Redis 3.2 的该方法底层发 `GETDEL`，而 `GETDEL` 是 Redis 6.2 才引入的指令。已改用 Lua 脚本绕过（见 `VerifyCodeServiceImpl.java:96-115`）。

### 版本事实（有据可查）

- MySQL 8.4 LTS：GA 2024-04-30，Premier 支持至 2029-04-30，Extended 支持至 2032-04-30
- MySQL 9.0 Innovation：GA 2024-07-01，**EOL 2024-10-15**（下一个版本发布当天）
- MySQL 官方明确：**Innovation 版本降级需逻辑导出（`mysqldump`）再导入，不支持原地降级**

## Decision

**三条规则，同时生效：**

### 规则 1：生产用 MySQL 8.4.x LTS，本地加装 8.4 实例作为 dev 主库

- 生产：MySQL **8.4.x LTS**（唯一受支持的长期版本选择）
- 本地：**加装 MySQL 8.4 LTS 实例**（端口 3307，服务名 `MySQL84`），dev 直接连 8.4
- 连接器：`mysql-connector-j` 保持 **8.4.0**（用户明确要求，勿升 9.x），与服务端主版本对齐
- 字符集：`utf8mb4` / `utf8mb4_unicode_ci`

**为什么本地要加装而不是"凑合用 9.0"**：9.0 → 8.4 是降级，官方要求逻辑 dump+load。若本地一直在 9.0 上开发，上线当天才做首次导出导入，遇到类型/语法不兼容时没有缓冲。提前切到 8.4 是把风险前置。

### 规则 2：生产用 Redis 7.2.x，但代码一律按 Redis 5.0 语义编写

- 生产：Redis **7.2.x**
- 本地：Redis **5.0.14.1 保留不动**（Windows 版，用户已装）
- **代码基线：必须能在 Redis 5.0.14.1 上跑通**

这个组合看着矛盾，实际是最优解：本地跑 5.0（不折腾重装），生产跑 7.x（新版本更安全、性能更好），而代码按**最严基线 5.0** 写 —— 因为 7.x 向下兼容 5.0 的指令集，所以"能在 5.0 跑"就"一定能在 7.x 跑"，两边都安全。反过来（代码按 7.x 写）则本地直接崩。

### 规则 3：Redis 6.0+ 指令禁用清单（硬约束）

**禁用指令（6.0 / 6.2 / 7.0 新增，5.0 全部不支持）**

| 指令 | 最低版本 | 说明 |
|---|---|---|
| `GETDEL` | 6.2 | **已踩坑** |
| `GETEX` | 6.2 | |
| `SET ... EXAT` / `PXAT` | 6.2 | 绝对过期时间戳 |
| `SET ... KEEPTTL` | 6.0 | 覆盖写保留 TTL |
| `SET ... GET` | 6.2 | 返回旧值 |
| `LPOS` | 6.0 | |
| `ZRANDMEMBER` / `HRANDFIELD` | 6.2 | |
| `SMISMEMBER` | 6.2 | |
| `ZRANGESTORE` | 6.2 | |
| `COPY` | 6.2 | |
| `SINTERCARD` | 7.0 | |
| `EXPIRE` 的 `NX`/`XX`/`GT`/`LT` | 7.0 | |
| `STRALGO LCS` | 6.0 | |
| ACL / RESP3 / client-side caching | 6.0 | |

**Spring Data Redis API 禁用清单**

```java
// 禁用 —— 在 Redis 5.0 上必抛异常
redisTemplate.opsForValue().getAndDelete(key);
redisTemplate.opsForValue().getAndExpire(key, ttl);
redisTemplate.opsForZSet().randomMember(key);
redisTemplate.opsForZSet().distinctRandomMembers(key, n);
redisTemplate.copy(src, dst, true);
redisTemplate.expire(key, ttl, ExpiryPolicy.NX);

// 安全 —— 5.0 支持
redisTemplate.opsForValue().get / set / delete / increment
redisTemplate.opsForValue().setIfAbsent(key, val, Duration);  // 底层 SET NX PX
redisTemplate.expire(key, ttl);                               // 无选项
redisTemplate.execute(RedisScript, keys, args);                // Lua，原子
```

**Lua 替代写法清单**（新建 `util/RedisLua.java` 集中管理，禁止散落在各 Service）

```lua
-- 1) GETDEL 替代：原子取出并删除（已在 VerifyCodeServiceImpl.verify 使用）
local v = redis.call('GET', KEYS[1])
if v then redis.call('DEL', KEYS[1]) return v end
return ''

-- 2) GETEX 替代：取出并续期
local v = redis.call('GET', KEYS[1])
if v then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return v

-- 3) SET KEEPTTL 替代：覆盖写但保留原 TTL
local ttl = redis.call('PTTL', KEYS[1])
redis.call('SET', KEYS[1], ARGV[1])
if ttl > 0 then redis.call('PEXPIRE', KEYS[1], ttl) end
return 1

-- 4) 滑动窗口限频（G1 陌生人私信配额用这个）
-- ARGV: [1]窗口左边界毫秒 [2]上限 [3]当前毫秒 [4]成员 [5]窗口毫秒
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1])
local n = redis.call('ZCARD', KEYS[1])
if n < tonumber(ARGV[2]) then
  redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[5])
  return 1
end
return 0

-- 5) 分布式锁释放（check-and-del，防误删他人锁）
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

**纪律**：新增任何 Redis 调用前先问一句"Redis 5.0 有这条指令吗"。不确定就走 Lua。

## Consequences

**正面**
- 生产 MySQL 是受支持的 LTS 版本，到 2032 年有补丁
- 本地与生产同 MySQL 主版本，杜绝"本地跑通、生产报错"
- Redis 代码按最严基线写，本地与生产都安全
- 连接器 8.4.0 与服务端 8.4 对齐，无版本错配

**负面（必须承认）**
- **本地要装第二个 MySQL 实例**，约 0.5 天工作量，且本机内存占用增加（两个 MySQL 实例）
- **9.0 → 8.4 是降级，必须逻辑导出导入**。上线前要演练一次完整 dump+load，不是原地升级
- **Redis 5.0 是长期约束**：团队永远不能用 6.2+ 的便利指令。每写一个 Redis 调用都要多想一步
- 本地 Redis 5.0 与生产 Redis 7 的版本差意味着：某些在 7.x 上才有的行为（如客户端缓存）永远无法在本地验证

**验证要求（写进端到端验证步骤）**
- [ ] 全部流程必须在 **Redis 5.0.14.1** 上跑通，无 `ERR unknown command`
- [ ] 全部流程必须在 **MySQL 8.4** 实例上跑通（不仅是 9.0）
- [ ] 演练一次 `mysqldump`（本地 9.0）→ 导入 8.4 → 数据一致性校验
