# ADR-009: 设计令牌以 docs/design/design-tokens.css 为唯一准绳；旧 tokens.css 迁移而非并存

## Status

Accepted (2026-10-08) · 由 team-lead 裁定，架构侧落地

## Background

项目里出现了**两套设计令牌**，且值不一致：

| 文件 | 状态 | 覆盖 | 问题 |
|---|---|---|---|
| `frontend/src/styles/tokens.css` | 历史遗留，46 行，`main.js:5` 引入 | 只有圆角、间距、一个背景色 | ① 阴影用 `rgba(0,0,0,*)` 纯黑，命中设计红线 2；② `.el-card:hover` 是 `1px` 边框 + `blur 16px` 阴影，命中红线 3「幽灵卡片」；③ 字体栈缺 `HarmonyOS Sans SC`；④ 自定义变量用 `--app-bg` / `--card-radius` 命名，与 `--ys-*` 是两套命名空间 |
| `docs/design/design-tokens.css` | 设计师新出，含 `:root` 变量 + Element Plus Bridge + 基础重置 | 完整色板（对比度实测）、字体阶梯、间距 4px 网格、圆角、阴影三级、动效、断点、布局、触摸目标、图标规范 | 尚未接入前端 |

第 3 个漂移实例：`frontend/index.html:8` 的 `theme-color` 与 `design-tokens.json` 的 `color.accent` 不一致（登记为 TD-24）。

如果两套并存，前端照旧的写、设计照新的审，必然出现"设计稿与实现不一致"，且没人能说清哪个是对的。

另外还有一个必须一并解决的技术陷阱：Element Plus 的 `--el-color-primary` **家族**是一组 SCSS 编译期算好的独立变量（`--el-color-primary-light-3/5/7/8/9`、`--el-color-primary-dark-2`），不是运行时从主变量派生的。只覆盖主变量会让 hover / active / disabled 仍留在旧色系。

## Decision

**1. 唯一准绳：`docs/design/design-tokens.css`。**
`frontend/src/styles/tokens.css` 降级为**待迁移**，不再作为任何新样式的来源。

**2. 迁移方式（Phase 3 前端第一个 PR 内完成）**
- 把 `docs/design/design-tokens.css` 复制到 `frontend/src/styles/design-tokens.css`
- 删除 `frontend/src/styles/tokens.css` 中的**重定义部分**（`:root` 变量与 `.el-card` / `body` 覆盖）
- `tokens.css` 改为只做一件事：`@import './design-tokens.css';`（或直接删除该文件，`main.js` 改为 import 新文件）
- 旧变量 `--app-bg` / `--card-radius` / `--space-*` 全部替换为 `--ys-*` 对应项

**3. `--ys-*` 接入方式：引入顺序不可调换**

```js
// main.js
import 'element-plus/dist/index.css'   // 先：EP 自带变量与组件样式
import './styles/design-tokens.css'    // 后：本文件覆盖 --el-*（Bridge 段）
```

顺序不可调换的原因：CSS 变量在同一 `:root` 层叠中**后定义者胜**。若先引 tokens 后引 EP，EP 会把 Bridge 覆盖掉，整套配色失效且**没有任何报错**——这是一个沉默故障。

**4. `vite.config.js` 的 auto-import 配置不需要改**
`unplugin-vue-components` + `ElementPlusResolver` 负责的是**组件 JS 与组件级 CSS** 的按需引入，与本 ADR 的**全局 CSS 变量**是两条正交的路径，互不影响。
但需注意：本项目 `main.js:3-6` 同时存在 `app.use(ElementPlus)` + `import 'element-plus/dist/index.css'` 的**全量引入**，这与 `vite.config.js:20-31` 的按需配置冲突，导致按需失效、整包打包。已在 ARCHITECTURE.md 登记为 **TD-21**，修复时本 ADR 的第 3 条（引入顺序）会随之简化为只 import 一个 `design-tokens.css`。

**5. 为什么浏览器端不能出现两套 `--el-color-primary`（或任何 `--el-*`）**

设计师的 Bridge 段已经正确处理了这个陷阱——它不仅覆盖主变量，还把**整条派生链**都写成了显式值：

| 变量族 | 覆盖情况 | 证据 |
|---|---|---|
| `--el-color-primary` | 指向 `var(--ys-accent)` | `design-tokens.css:188` |
| `--el-color-primary-light-3 / -5 / -7 / -8 / -9`、`-dark-2` | **全部显式覆盖**（6 个） | `design-tokens.css:189-194` |
| `--el-color-success` 及其 6 个派生值 | 全部覆盖 | `design-tokens.css:196-202` |
| `--el-color-warning` 及其 6 个派生值 | 全部覆盖 | `design-tokens.css:204-210` |
| `--el-color-danger` 及其 6 个派生值 | 全部覆盖 | `design-tokens.css:212-218` |
| `--el-color-error` 及其 6 个派生值 | 全部覆盖 | `design-tokens.css:220-226` |
| `--el-color-info` 及其 6 个派生值 | 全部覆盖 | `design-tokens.css:228-234` |
| `--el-bg-color` / `-page` / `-overlay`、`--el-fill-color` 等 | 覆盖 | `design-tokens.css:237-241` |

即：**每个语义色都覆盖了 7 个变量（1 主 + 6 派生），不是只改一个主变量。**

**硬规则**：业务代码**禁止直接写 `--el-*`**。要改 EP 组件外观，改 `design-tokens.css` 的 Bridge 段，让所有消费方看到同一份值。

理由：
- EP 的 `light-*` 系列是 SCSS **编译期**算好的独立变量，运行时不会跟着 `--el-color-primary` 变。只改主变量 = 按钮底色对了、hover 还是旧蓝 —— 半套覆盖，最难查的那类视觉 bug
- 若业务代码里散落 `--el-color-primary: x`，与 Bridge 段形成两个 `:root` 定义，谁生效取决于样式表加载顺序，而按需引入下这个顺序**不保证稳定**
- 两套 `--el-*` 与两套 `--ys-*` 一样，都会让"设计稿对不上实现"变成无法归因的问题

**6. 断点落地：以设计师断点为准，禁用 EP 响应式属性**

| 档 | 设计师 | Element Plus 2.14.5 |
|---|---|---|
| xs | 0（< 640） | < 768 |
| sm | ≥ 640 | ≥ 768 |
| md | ≥ 768 | ≥ 992 |
| lg | ≥ 1024 | ≥ 1280 的上一档（1200） |
| xl | ≥ 1280 | ≥ 1920 |
| 2xl | ≥ 1536 | — |

**完全错位**（EP 的 `sm=768` 是设计师的 `md`；EP 的 `md=992` 在设计师体系里根本没有）。

**硬规则**：禁用 `el-col` 的 `:xs` / `:sm` / `:md` / `:lg` / `:xl` 响应式属性。栅格一律用 CSS Grid + `@media (--ys-bp-*)`。

落地方式：
- CSS 侧：加 `postcss-custom-media`（1 个 devDependency），在 `design-tokens.css` 顶部定义 6 条 `@custom-media --ys-bp-sm (min-width: 640px)` 等。CSS 变量**不能**用于媒体查询，所以只有 custom-media 或写死 px 两条路，没有第三条。
- JS 侧：`src/composables/useBreakpoint.js` 用 `matchMedia` 读同一组数值（弹窗全屏、抽屉方向需要 JS 判断）。

## Consequences

**正面**
- 设计令牌只有一个来源，"设计稿对不上实现"可以归因
- 完整色板带实测对比度，无障碍（WCAG AA）有据可查
- EP Bridge 一次覆盖整条派生链，不会留下半套配色
- 断点与间距、字号同属一份令牌，不会出现"布局对齐了但间距不对"
- 暗色模式已预留 `:root[data-theme="dark"]`，将来加一行属性即可

**负面（必须承认）**
- **断点值会同时存在于三处**：`design-tokens.json`（源）、`design-tokens.css` 的 `@custom-media`、`useBreakpoint.js` 的常量。改断点必须三处同改，这是**手工同步，有漂移风险**。消除它需引入生成脚本（+1 devDep + 构建步骤），对单人 MVP 不划算，故接受手工同步 + 在 `design-tokens.css` 顶部写明同步纪律
- 迁移期两个文件会短暂共存，`main.js` 引入顺序错了不会报错，只会静默失效 —— 必须在 PR 里明确检查
- 设计师的 tokens 里 `light-*` 派生值是硬编码的，意味着**换主色必须重算整条派生链**（设计师已实测对比度，换色需要重新实测）
- 旧业务代码里已有的 `--el-*` 直接引用（若有）需要逐一清理，这是迁移工作量的一部分

**验证要求**
- [ ] `main.js` 引入顺序：`element-plus/dist/index.css` 在前，`design-tokens.css` 在后
- [ ] 构建产物里 `--el-color-primary` 只被定义一次（Bridge 段），`--ys-accent` 只被定义一次
- [ ] 用浏览器 DevTools 检查任意 EP 按钮的 hover 态，确认用的是新色系而非 EP 默认蓝
- [ ] 旧 `tokens.css` 的重定义部分已删除，仅保留 import
