# ADR-010: school_major 是否启用物理外键

## Status

**Accepted（2026-11-01）——采用方案 B：不启用物理外键。** 2026-11-01 完成只读数据审计，结果见下文；同日用户确认按 B 收口。本决定不改变生产结构（生产本来就是 0 外键），仅让 `sql/schema.sql` 与生产一致。

## Background

`sql/schema.sql` 曾为 `school_major` 定义了全项目唯一一个物理外键（2026-11-01 已按方案 B 移除）：

```sql
CONSTRAINT `fk_major_dept` FOREIGN KEY (`dept_id`)
    REFERENCES `school_dept` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE
```

但 2026-10-31 生产实测与恢复演练确认：

- 生产库 `information_schema.referential_constraints` 为 **0 个外键**；
- 用生产备份恢复出的临时库同样为 0 个外键；
- 生产 `school_major` 仍是旧结构：`dept_id` 为 `int`，多旧列 `is_confirmed`，缺 `uk_school_code`、`uk_dept_name`、`idx_dept_level_enabled_sort`，只有主键、`idx_dept`、`idx_code`；
- 根因是 `migration_f12_school_major.sql` 使用 `CREATE TABLE IF NOT EXISTS`，对已存在的旧表整段跳过，后续从未升级。

应用层现状：

- 注册/引导写入前，`DictServiceImpl.requireSelectableDept` 校验学院，`requireSelectableMajor` 校验专业属于该学院且启用；
- 项目没有删除学院/专业的后台接口，字典通过 SQL 种子与修复脚本维护；
- 因此当前数据完整性主要由应用层与人工 SQL 纪律保证，物理外键只额外拦截手工 SQL 写入的孤儿专业。

## Options

### A. 补齐物理外键（原推荐，前提是审计干净；已否决）

在恢复库先演练，再对生产执行：
1. 审计孤儿、重复专业码/专业名；
2. 对齐 `dept_id` 类型并补唯一索引/组合索引；
3. 添加 `fk_major_dept`；
4. 验证应用写入与部署包回归。

优点：与 `schema.sql` 的原始设计一致；学院被引用时无法误删；手工 SQL 维护字典时能拦住孤儿。
代价：需要一次 DDL 迁移和恢复演练；若存在历史孤儿或重复数据，要先清理/确认。

### B. 明确采用应用层完整性（不启用物理外键）

从 `schema.sql` 移除 `fk_major_dept`，在架构文档写明“本项目不依赖数据库外键，完整性由应用层与迁移脚本保证”。

优点：与生产 0 外键现状一致；零 DDL 风险；新建库与生产结构一致。
代价：失去唯一一道物理约束；手工 SQL 维护字典时更容易写入孤儿。

## Decision

**采用方案 B：项目不启用物理外键，完整性由应用层与迁移脚本保证。**

落地内容（2026-11-01）：

1. `sql/schema.sql` 移除 `school_major.fk_major_dept`，全库 0 物理外键；
2. `sql/schema.sql` 表注释与文件头统一写明「不建 FK 约束，由应用层保证一致性」；
3. 本文保留方案 A 的审计与迁移草案，仅作将来重议时的参考，不再执行；
4. `sql/migration_f12_school_major.sql` 与 `sql/migration_2026-10-23_baseline_sync.sql`
   是历史迁移，保留原样仅作存档，不纳入当前部署包；新库以 `schema.sql` 为准。

不选 A 的直接原因：唯一索引前置条件不成立（`020302` 双行、学院 5 本/专同名），
先补外键会把有争议的重复数据固化；而孤儿审计为 0 说明应用层校验已经守住当前数据。

遗留事项（与本次决策分开处理）：`020302` 双行与同院本/专同名的业务口径需要产品确认；
`school_major` 的 `dept_id` 类型（`int` → `bigint`）与缺失索引如需对齐，另开幂等迁移，
不与外键决策混做。

## Data Audit（在恢复库执行，不碰生产）

```sql
-- 1. 孤儿：专业指向不存在的学院
SELECT COUNT(*) AS orphan_majors
FROM school_major m
LEFT JOIN school_dept d ON d.id = m.dept_id
WHERE d.id IS NULL;

-- 2. 指向停用/逻辑删除学院的专业（不是孤儿，但需确认业务含义）
SELECT COUNT(*) AS disabled_dept_refs
FROM school_major m
JOIN school_dept d ON d.id = m.dept_id
WHERE d.enabled = 0 OR d.is_deleted = 1;

-- 3. 重复专业码（同一学校内 code 必须唯一）
SELECT school_id, code, COUNT(*) AS n
FROM school_major
WHERE is_deleted = 0
GROUP BY school_id, code
HAVING COUNT(*) > 1;

-- 4. 重复专业名（同一学院内 name 必须唯一）
SELECT dept_id, name, COUNT(*) AS n
FROM school_major
WHERE is_deleted = 0
GROUP BY dept_id, name
HAVING COUNT(*) > 1;

-- 5. 类型对齐确认
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE
FROM information_schema.columns
WHERE table_schema = 'campus_social_v2'
  AND table_name IN ('school_major', 'school_dept')
  AND column_name IN ('id', 'dept_id');
```

判定：第 1 类必须为 0；第 2 类需确认允许保留；第 3/4 类必须先去重后才能建唯一索引。

## Data Audit Results（2026-11-01，本地恢复库）

审计脚本：`sql/audit_adr010_school_major.sql`（只读 SELECT）。

数据源：`backup_campus_social_v2_before_clean_20261026.sql` 导入临时库
`campus_adr010_audit_20261101`（39 表，含 9 个真实用户），并在当前开发库
`campus_social_v2` 复跑；两库字典数据一致（7 学院 / 62 专业 / 4 年级）。

| 检查项 | 结果 |
| --- | --- |
| `school_major.dept_id` 孤儿（全部行 / 未删除行） | **0 / 0** |
| `school_major.dept_id` 为空 | 0 |
| `user.dept_id` / `major_id` / `grade_id` 孤儿 | **0 / 0 / 0** |
| `user` 专业不属于所填学院 | 0 |
| `user` 引用停用/删除的学院或专业 | 0 / 0 |
| `user` 只填专业未填学院 | 0 |
| 同校专业码重复 | **1 组**：`020302` → id=23（学院 2，金融工程）、id=27（学院 5，金融工程），均未删除 |
| 同院专业名重复 | **1 组**：学院 5「电子商务」→ id=32（120801，本科）、id=36（530701，专科），均未删除 |
| 列类型 | `school_dept.id` = `bigint`；`school_major.dept_id` = `int`（不一致） |
| 现有索引 | `school_major` 只有主键、`idx_dept`、`idx_code` |

**结论**：

1. **孤儿数据干净**：校级字典与用户引用在样本中无孤儿、无跨学院错配，应用层校验
   （`requireSelectableDept` / `requireSelectableMajor`）迄今没有留下脏数据。
2. **ADR 原提议的唯一索引不能照搬**：
   - `uk_dept_name(dept_id, name)` 会把「同学院同名但不同层次（本科/专科）」误判为冲突；
     至少应改为 `(dept_id, name, level)`，或先与业务确认是否允许同名本/专并存。
   - `uk_school_code(school_id, code)` 会与真实存在的 `020302` 双行冲突；
     必须先确认这两条「金融工程」是重复种子还是两学院各自开设，再谈唯一约束。
3. **类型不一致仍需处理**：若走选项 A，`dept_id` 必须先 `int → bigint`，
   否则外键无法建立。

**范围限制**：本机没有 ECS SSH，未重新导入 2026-11-01 的生产备份；上述样本是
2026-10-26 的生产快照（上线前清理基线），并在当前开发库复跑得到同样结论。
生产当前字典数量未在本机核对；在执行任何 DDL 前，必须在最新恢复库或生产只读连接上
复跑同一脚本。

**审计结论**：采用 **B（0 外键）**。理由：孤儿为 0 说明应用层已守住；项目没有删除
学院/专业的后台接口，外键的边际收益低；而 ADR 原迁移中的两个唯一索引会直接失败或
误伤合法数据，需要先做产品口径确认。若未来重议 A，建议只做「类型对齐 + 外键」，
唯一索引另开迁移并先清理 `020302` 重复。

## Consequences

- 选 A：`schema.sql` 与生产长期一致，但需要一次受控 DDL；旧表结构差异（`is_confirmed` 等）需在同一次迁移中决定是否清理。
- 选 B：不再有“schema.sql 说有、生产没有”的模糊状态，但放弃物理完整性约束。
- 无论选哪个，恢复演练脚本都不应把外键数量当作备份是否损坏的判据；它只应记录生产真实结构。

## Decision Owner

用户。2026-11-01 确认采用方案 B；生产与 `schema.sql` 均保持 0 外键。
