## 二、P1：较严重（正确性 / 一致性 / 性能）

### P1-1 并发 refresh：18/20 线程拿到 `-1` 而非 `REUSED`（测试红）

**证据**：`AuthServiceImpl.java:96-107` 的 Lua CAS：
```lua
if cur == false then return -1 end          -- key 不存在
if cur ~= ARGV[1] then redis.call('DEL', KEYS[1]); return 0 end   -- jti 不匹配（重用）
redis.call('SET', KEYS[1], ARGV[2], 'EX', ...); return 1
```
实测分布 `winners=1 reused=1 others=18`：**第一个线程 SET 了新 jti 后 key 仍存在**，其余线程应读到 `cur ≠ oldJti` 返回 `0`。实际得到 `-1`（key 不存在）说明**渠道 0 的 `DEL` 抢在了别的线程 `GET` 之前** —— 即第一个失败者吊销后，后续线程全部落到「key 不存在」分支。

**影响**：功能上是安全的（都拒绝），但**语义失真**：真正的「重用攻击」被误报为「token 自然过期」，安全事件被降级成普通失效，告警与审计无法区分。测试断言（`reused == 19`）因此永远不可能成立。

**修复**：要么把「已吊销」用独立 tombstone key 表达（`DEL` 后写 `refresh:revoked:{uid}`，TTL 同 token），让后续请求区分两种失败；要么修正测试断言为「恰好 1 个成功、其余全部被拒且无其它异常」。

## 四、做得好的地方（避免修复时误伤）

1. **JWT 双 token 设计正确**：access/refresh 用**两把独立密钥** + `typ` claim 双重校验（`JwtUtil.java:93-120`），跨类型不可混用；HS512 密钥长度在启动时断言（`JwtConfig.java:42-47`）。
2. **refresh rotation 的 Lua CAS 是原子的**（`AuthServiceImpl.java:96-107`），单次执行完成「读-比对-写/删」，杜绝并发双花。
3. **`@RequireAdmin` / `@RequireVerified` 确实生效** —— 这是重点怀疑对象，已排除：两个拦截器都从 `HandlerMethod` 取注解并支持类级（`AdminInterceptor.java:40-47`、`VerifiedInterceptor.java:52-60`）；`/admin/**` 五个控制器均有类级 `@RequireAdmin`。
4. **`VerifiedInterceptor` 是 fail-closed（401）**，不是 fail-open（`VerifiedInterceptor.java:61-76`）。
5. **CORS / WS origin 都不回落通配符**：`CorsProperties.resolveOrigins()` 逐项过滤 `*`，三级来源（env > 配置 > localhost）全空时只给 localhost。
6. **BCrypt cost=12**，登录失败统一 `WRONG_PASSWORD` 不区分「账号不存在」。
7. **逻辑删除 + 唯一键的坑已被系统性处理**：`like`、`relation`、`activity_signup`、`circle_member`、`post_favorite`、`group_read`、`user_tag`、`post_topic`、`feed_item`、`group_message`、`comment`、`post` 的取消/退出全部走**物理删除**，且注释都解释了原因。唯一漏网的是 `topic`（P1-21）。
8. **事务边界总体正确（93 处 `@Transactional`）**，且**自调用问题已被识别**：`TagServiceImpl.java:110-112` 注释明确写了代理失效并把事务挂在外层。`PostServiceImpl` 委托独立 Bean `writeService`，代理正常。
9. **事务内不做 HTTP/LLM/WS**：`PostNotifySupport.scheduleAiReviewAfterCommit`（`:48-61`）用 `TransactionSynchronization.afterCompletion(STATUS_COMMITTED)` 推迟 LLM；`AiReviewTriggerImpl` 再叠 `@Async("llmExecutor")`；`WsAfterCommit.java:34-45` 推迟 WS。**这三处是全库事务边界处理最好的部分**（唯一漏的是 P1-12）。
10. **防超卖正确**：`ActivityMapper.trySignin`（`:19-25`）的 `WHERE (capacity=0 OR current_count<capacity) AND status IN (0,1,2)` + 原子 `+1`，配 `uk_as` 幂等键；`cancelSignin` 用 `GREATEST(0, ...)` 防负。
11. **SQL 注入面极小**：全库唯一 `${}` 是 `PostMapper.java:161` 的 `selectFeedBySql`，其调用面 `PostFeedQueryService.buildFeedSql` 的 `sortCol` 走白名单（`:153-159`）、其余是 `Long`/`int` —— **当前确实不可注入**（`size` 的 clamp 依赖上游，见 P1-5）。`LIKE` 全部 `CONCAT('%', #{kw}, '%')` 或 MP `.like()`，`IN` 全部 `<foreach>#{i}</foreach>`。
12. **全库无 `OFFSET` 深分页**，统一 id 游标。
13. **全项目无 `v-html` / `innerHTML`**，用户内容一律 `{{ }}` 插值；无 `javascript:` 协议注入点；Element Plus 按需引入未退化。
14. **用户脱敏装配器设计正确**：`UserVoAssembler.of` / `ofPrivate` 严格区分「他人卡片」与「我的资料」，他人卡片不含 `role` / 邮箱 / 未读数（问题只在 P1-22 那 4 处绕过它）。
