## 第一部分 · 推广阻断项（⛔ 不解决就别发）

这些不阻塞「代码能不能跑」，但会直接决定「推广成不成立」。

- ⛔ **冷启动没有抓手**
  - 现象：推荐（同班/同院系）依赖 `user.dept/grade/major`，而这些字段只有「学号过了六层校验」的人才有。校验越严 → 能匹配的人越少 → 新用户觉得「里面没我认识的人」→ 流失。
  - 位置：`CampusVerifyServiceImpl.submitStudentNo`、`docs/plan-nav-and-identity.md` §5.1。
  - 要回答：第一批种子用户从哪来？能否绕过「过认证才有归属数据」的死锁（例如先有班级/院系粗匹配，认证后置补强）？
- ⛔ **身份「事前确证」做不到，只剩事后兜底**
  - 现象：无名册 + 无校园邮箱前提下，六层校验只挡「只有一个学号」的人；「知道全部规则的人」可冒充。残余风险 = 事后发现 + 举报 + 下线。
  - 位置：`docs/plan-nav-and-identity.md` §3.1、§3.4；`CampusVerifyServiceImpl.validateStudentNoAgainstProfile`。
  - 要回答：是否明确接受「事后确证」这个价值观（该文件 §7.4 待拍板）？被冒名者满校园发内容，会直接毁掉「这是某大学的 App」的信任。
- ⛔ **合规与内容责任（校园尤其要当心）**
  - 现象：有 LLM 审核 + 敏感词 DFA（`LlmModerationServiceImpl`、`SensitiveWordFilter`），能力有了；但「谁 7×24 审、出事走什么流程、平台责任边界」是运营空白。
  - 位置：`backend/src/main/java/com/campus/social/service/impl/LlmModerationServiceImpl.java`、`util/SensitiveWordFilter.java`。
  - 要回答：出事（违规图/视频/舆情）的处置 SOP 谁来执行、多久响应？

## 第二部分 · 推广前该补的短板（⚠ 强烈建议）

都是「能跑起来推广」的短板，不是代码优雅度问题。

### A. 可观测性（现在基本是盲飞）

- ⚠ **数据看板缺失**。推广期必须能回答：今天多少人注册被六层挡了、挡在几层、7 日留存多少。
  - 埋点：六层校验失败已写 `log.warn`（`CampusVerifyServiceImpl.mismatch`），但没进报表。对应 `docs/plan-nav-and-identity.md` §5.2「未收录埋点」尚未做。
- ⚠ **没有留存/漏斗指标**。注册 → 过认证 → 发起首次搭话 → 7 日回访，这条漏斗没有一处能看。

### B. 认证规则的脆弱性（架构级）

- ⚠ **学号编码规则写死在代码里，换校/换规则要发版**
  - 位置：`CampusVerifyServiceImpl.STUDENT_NO_FORMAT`（`^(\d{2})(\d{4})(\d{2})(0[1-9])0?[56](\d{2})$`）、`MAX_CLASS_RANK=69`、`parseLevelMarker` 的 `05/06` 取值。
  - 风险：学制改革、转专业、换编码规则 → 整套认证作废。
  - 建议：把位数/层次标记/上限下沉到配置或字典表（§5.2 已提「字典运营化」，但学号规则本身还没运营化）。
- ⚠ **`MAJOR_CLASS_TO_DEPTS` 硬编码在 Java**（新增专业要发版）。位置：`service/support/StudentNoAutoPassSupport`（交叉校验映射）。

### C. 误挡的真实同学——翻案太慢

- ⚠ **推广期申诉 = 等 24h 人工**（`REVIEW_ESTIMATED_HOURS=24`）。新用户 3 天过不了认证就流失。
  - 位置：`CampusVerifyServiceImpl.submitStudentNo` 返回的 `estimatedHours`；申诉通道（在途）`FeedbackServiceImpl.submitStudentNoAppeal`。
  - 建议：给管理员一个**即时放行**入口，别一律排队。
- ○ 在途的申诉通道（公开端点 `/auth/appeal-student-no` + 邮件回执）是正解方向，但把「未注册用户的敏感凭证（学号+邮箱）」塞进 `feedback` 表、靠 `user_id=NULL` + content 前缀区分——**能跑但是技术债**：将来反馈模块加「按用户统计 / 用户视角列表」时 NULL 会漏进来。记着，见 §5.2。

### D. 登录/注册限流（部分覆盖，有洞）

- ⚠ **验证码发送有严格限流**（`VerifyCodeServiceImpl`：60s 单邮箱 + 每日 20 封，`code:limit:` SET NX）——这块是好的。
- ⚠ **但登录/注册本身没有 IP 级限流**（`AuthServiceImpl.register/login` 无 throttle）。§3.4 决策 4 的「按 IP + 设备限流」尚未落地。
  - 风险：学号 13–14 位，遍历成本低；`STUDENT_NO_EXISTS`/`USERNAME_EXISTS` 明确报错 = 可批量扫出在册学号（`docs/plan-nav-and-identity.md` §3.4 决策 2「注册错误模糊化」）。
  - 建议：登录/注册按 IP + 设备限流；「已存在 / 格式非法」的错误**统一模糊化**，别当枚举 oracle。
- ⚠ **登录失败无锁定/退避**（`AuthServiceImpl.login` 连错不递增惩罚）。弱口令 + 学号可枚举 → 撞库面较大。

## 第四部分 · 工程质量本身（现状评估，无需新增动作）

这一档我判断**已达标**，列出来是为了说明「推广不够的原因不在这里」：

- ✅ 分层干净：controller 零业务、service `@Transactional`、统一异常体系、Redis Lua CAS。
- ✅ 并发正确：`StrangerQuotaServiceImpl` 按日分桶 + 竞态取舍注释、refresh jti CAS、活动报名防超卖。
- ✅ 安全自觉：六层报错收敛、CORS 白名单、防账号枚举、防邮箱多绑、`application-local.yml` 已 gitignore、生产密钥走环境变量。
- ✅ 可维护性：逐方法中文注释 + 引 SPEC/AC 编号。
- ✅ 测试集中在真会出事处：refresh jti、活动报名超卖、学号解析、OSS 签名（48 用例）——但缺 CI/Testcontainers 化（集成测试连本机 Redis/DB）。
- ✅ 文档全：PRD/SPEC/ARCHITECTURE/decisions + 上线复盘/排障复盘。

> 一句话：**代码够撑住前 5000 人，撑不起「让用户来」和「证明这些是真学生」。**
