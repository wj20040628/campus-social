# 推广前三大改造 · 落地方案（对「推广前检查清单」⚠ 部分的钻取）

- 日期：2026-10-19
- 依赖：`docs/推广前检查清单.md` 优先级总表 1/2/3。
- 原则：**全部走配置/字典/管理端,不重发版改认证逻辑主体**;每条给出「动哪个文件 + 新表/新端点 + 迁移脚本 + 测试锚点」,可直接开工。
- 三个改造彼此独立,可分批落地。下面每块都以「为什么 → 现状证据 → 具体改动 → 验收」组织。

## 改造 1 · 学号规则外置成配置（清单 §B,优先级 2）

### 为什么

六层校验的「位数 / 层次标记取值 / 班内序号上限 / 年级」现在**写死在代码里**,换校或学校改编码规则就要发版重写:

- `CampusVerifyServiceImpl.STUDENT_NO_FORMAT` 正则(位数 + 层次 05/06 取值)
- `CampusVerifyServiceImpl.MAX_CLASS_RANK = 69`
- `CampusVerifyServiceImpl.parseLevelMarker` 硬编码 `"05"/"5"/"06"/"6"`

### 现状证据(已核实)

- 项目**已有配置注入范式**:`CampusProperties`(`@ConfigurationProperties(prefix="campus")`),`dailyNewPeerLimit`、`autoApproveStudentNo` 等全是配置项,注释明确写着「改一次要发版=反模式」。学号规则漏在这个范式之外,是**一致性的洞**,不是新架构。
- 项目**已有字典范式**:`school_major` / `school_dept` / `school_grade`(migration_f12),`DictService` 读它们。
- `StudentNoAutoPassSupport.MAJOR_CLASS_TO_DEPTS`(专业大类→学院映射)**仍是 Java 静态 Map**——清单 §B 第二条要一并收编。

### 具体改动

**A. 把「位数/层次/上限」收进 `CampusProperties`**(配置,不改表):

新增字段(均带默认值 = 现值,保证不改配置也行为不变):

```java
/** 学号总长度白名单,逗号分隔;默认 "13,14"。替代 validateStudentNoAgainstProfile 里 13/14 的硬判断 */
private String studentNoLengths = "13,14";
/** 层次标记取值:本科,逗号分隔;默认 "05,5"。parseLevelMarker 不再硬编码 */
private String levelMarkerUndergrad = "05,5";
/** 层次标记取值:专科,逗号分隔;默认 "06,6" */
private String levelMarkerVocational = "06,6";
/** 班内序号上限,默认 69。替代 MAX_CLASS_RANK 常量 */
private int maxClassRank = 69;
```

并加 `resolveStudentNoLengths(): Set<Integer>` / `resolveLevelMarkers(level)` 这类解析方法,风格对齐现有的 `resolveEmailDomains()`。

改动落点:

- `CampusVerifyServiceImpl.validateStudentNoAgainstProfile`:
  - 长度判断改用 `campus.resolveStudentNoLengths()`
  - `MAX_CLASS_RANK` 改用 `campus.getMaxClassRank()`
- `CampusVerifyServiceImpl.parseLevelMarker`:改用 `campus.resolveLevelMarkers(...)`,不再硬编码 05/06。
- `StudentNoAutoPassSupport`:`MAJOR_CLASS_TO_DEPTS` 从 `static final Map` 抽成**读 `school_major` 字典**(用 `major.code` 前 4 位 大类 ↔ `major.deptId` 聚合)。**新增专业/学院时改字典表即可,不再补 Java 行**。
  > 注意:字典聚合出的「大类→学院」可能与现 Map 不完全等价(现 Map 里有跨学院的多值,如 0802)。落地时以「`SELECT DISTINCT dept_name FROM school_major WHERE code LIKE '0802%'`」验证等价,不等价的那几行才需要保留一份「例外映射」配置项。**这一步要写单测锁死等价性,别静默改变放行结果。**
- `STUDENT_NO_FORMAT` 正则(校验层)**仍保留为格式闸门**(它挡「非 13/14 位」「非纯数字」这种,成本低、不泄露规则,注释 `RegisterDTO` 已公开 `\d{13,14}`)。但**位数白名单**必须与 `campus.studentNoLengths` 同步,别两处漂移——建议正则改为**运行时由配置生成**,或至少在启动时 `@PostConstruct` 校验配置位数 ⊆ 正则允许集。
- 前端 `Register.vue` 的本地 validator(现有 13/14 位判断)→ 走 `useDictStore` 拉一份「学号规则配置」的只读端点,或至少把「13/14」常量改成从字典拉。**这一步可以和后端的「学号规则只读端点」合并**(见下)。

**B. 一个只读的「学号规则」管理端点**(让管理员/换校时不改代码):

- `GET /admin/dict/studentno-rule` 返回当前生效的位数/层次/上限/大类映射,供「学号核验」页展示与人工核对。
- 若决定规则**可由管理员在线改**:落 `dict_config` 表(键值)+ 启动/修改时重载 `CampusProperties`。**默认先做只读展示,在线写是增强项**(改规则是高危动作,不冒进)。

**C. 迁移脚本**:`sql/migration_x_studentno_rule.sql`

- 若规则下沉到 `dict_config` 表:建表 + 种子现值。若只进配置文件,则**无 DDL**,把现值写进 `application.yml` 的 `campus.*` 段,`application-local.yml` 同步。

### 验收

- 单测:`CampusVerifyServiceImplTest`(可新建)锁死「默认配置下,六层判定结果与改造前逐例一致」。这是**行为不变回归**,防止外置引入放行漂移。
- 换位数/上限只改配置后,一条真实学号样例能在新配置下通过/被拒,且不改任何 Java。
- 前端 `Register.vue` 的 13/14 判断与后端配置同源。

## 改造 2 · 管理员「即时放行」入口（清单 §C,优先级 3）

### 为什么

被误挡的真实同学,现在要么走**申诉等 24h 人工**,要么在「学号核验」队列里排队。推广期这个太慢 = 直接流失。要给管理员一个**当场放行**的能力,而不是只能「通过待审列表」。

### 现状证据(已核实)

- **`AdminVerifyController` 已有 `/{userId}/approve`**(立即 `verify_status=1` + `audit verify_approve`)。这已经是「即时放行」的原子能力——**缺的不是能力,是入口**:它挂在「pending 列表」里,而「被六层挡下、根本没进 pending」的用户,管理员在 pending 里**看不到他**,无从点 approve。
- 被挡的用户分两种:
  1. **没学号/没注册成功**(申诉通道那批,`feedback` 里 `user_id=NULL`)——没有 user 可 approve。
  2. **注册了但六层挡在 pending**(有 user,`verify_status=2`)——pending 列表已能 approve。
- 真正缺的是**第 1 类**:管理员拿到申诉(学号+邮箱),需要一个「凭学号找到该用户并放行 / 找不到就引导他重新注册」的通路。

### 具体改动

**A. 「学号核验」页加一个「按学号检索」**(补入口):

- `GET /admin/verify/by-student-no?studentNo=xxx` → 返回该学号对应的 user(若存在)及其 verify_status。
- 前端「学号核验」页(`views/AdminVerify.vue`)顶部加一个学号输入框 + 检索;检索到后复用现有 `approve` 按钮**即时放行**,检索不到显示「该学号尚无账号,请让对方重新注册(会走申诉/注册)」。

**B. 申诉队列(在途 `feedback`)处置动作 = 放行**:

- 在 `AdminFeedback.vue` 的申诉行(在途已加「认证申诉」角标 + mailto 邮箱)上,处置成功(采纳)时,**若管理员勾了「并放行该学号」**,后端 `FeedbackServiceImpl` 采纳回调里顺带:按 content 里的学号找 user → `approveVerify`。
- 更干净的:**把「放行」做成核验页的一等动作,而非塞进 feedback 处置**(避免跨模块耦合)。feedback 只负责「这是条申诉、联系邮箱是 X、去核验页处理」。→ 推荐这个,feedback 保持薄。

**C. 「重新认证」入口**(对应 plan §7.3 转专业人工修正):

- 已认证用户改学号走 `StudentNoChangeSupport.apply`(现有),但**转专业(专业变了、学号不变)**&#x73B0;在没有通路。
- 加 `PUT /admin/verify/{userId}/reverify-student-no` + 前端核验页动作,管理员直接改该用户的学号/专业并强制重新跑六层,或**直接置已认证**(跳过六层,因为管理员已人工确认)。**后者更快**,审计 action 记 `verify_admin_override`。

### 迁移脚本

- 无 DDL(复用 `user.verify_status` + `audit_log`)。仅在 `ResultCode` 增 `verify_admin_override` 的审计常量(Java 常量,非表)。

### 验收

- 管理员在核验页按学号检索到一个「已注册但 pending」的用户,一点即放行,用户端 `verify_status=1` 即时生效(不用等 24h)。
- 检索到一个「被申诉、还没账号」的学号,给出「尚无账号」明确提示,不报错。
- 每个放行/override 都有 `audit_log` 可追溯(谁、何时、放行哪个学号)。

## 改造 3 · 数据看板:注册被挡分布 + 留存（清单 §A,优先级 1）

### 为什么

推广期没有「今天多少人被六层挡了、挡在第几层、7 日留存多少」的可见性,冷启动全靠盲猜。而**挡在第几层**的数据其实已经存在——`CampusVerifyServiceImpl.mismatch` 已把「L3 年级 / L4 层次 / L5 专业码 / L6 班内序号 + 具体比对值」写进 `log.warn` 和 audit。**缺的是把它落库成可查的报表**,而不是散在日志里等 grep。

### 现状证据(已核实)

- `mismatch(...)` 已带 `layer` + `detail`(哪层没过、两边值),但只 `log.warn`,不进库。
- `audit_log` 是多态、只增不删的现成表,已有 `verify_student_no_submit` 记录。

### 具体改动

**A. 一张轻量埋点表** `verify_reject_stat`(按日 + 层级聚合,不存个人数据):

```sql
CREATE TABLE IF NOT EXISTS verify_reject_stat (
    stat_day    DATE       NOT NULL,
    reject_layer TINYINT  NOT NULL COMMENT '挡在哪层:3年级 4层次 5专业码 6班内;1/2 是格式层,单列',
    reject_cnt  INT       NOT NULL DEFAULT 0,
    PRIMARY KEY (stat_day, reject_layer)
);
```

- 在 `mismatch(...)` 里**顺手** `INSERT ... ON DUPLICATE KEY UPDATE reject_cnt = reject_cnt + 1`(与业务同事务或异事务皆可,报表用途允许异步)。
- 只存「第几层、几个」,**不存学号/邮箱等 PII**(合规:报表不夹带个人数据;需要反查具体某条时去 `audit_log`/log)。

**B. 一个只读端点 + 管理页「看板」tab**(`views/AdminVerify.vue` 或独立 `views/admin/Dashboard.vue`):

- `GET /admin/verify/reject-stats?days=30` → 近 30 天各层被拒曲线。
- 展示「哪层拒得最多」——**这直接告诉运营:是专业字典缺了(L5)、还是学号规则又变了(L3/L4)**。这正是 plan §5.2「未收录埋点」要的。

**C. 留存(次日/7 日)**:

- 不新建埋点表:用现有 `user.create_time` + `login` audit(`audit_log.action='login'` 的 `create_time`)按「注册后第 N 天是否有登录」聚合。
- `GET /admin/dashboard/retention` 返回 D1/D7 留存。**这是聚合查询,注意别在推广量起来后变成全表扫**——给 `audit_log` 补 `(action, create_time)` 或按 user 建索引。

**D. 端点归属**:都放 `/admin/**`,复用 `AuthInterceptor` 的 admin 鉴权(与 `AdminVerifyController` 同套)。

### 迁移脚本

- `sql/migration_y_verify_reject_stat.sql`:`verify_reject_stat` 建表 + `audit_log` 补索引。

### 验收

- 造 N 条故意错的学号(分别错在 L3~L6),看板能在当天看到对应层 +1。
- 留存端点能回答「昨日注册的人,今天有多少人回来登录」。
- 报表**不含 PII**,PII 反查走 audit_log。

## 落地顺序与工作量

| 序 | 改造           | 主要产出                   | 预估                 | 依赖                |
| - | ------------ | ---------------------- | ------------------ | ----------------- |
| 1 | 数据看板(改造 3)   | 埋点表 + 端点 + 看板页         | 中                  | 无                 |
| 2 | 学号规则外置(改造 1) | 配置/字典收编 + 等价性单测        | 中偏大(有回归风险,须锁死默认行为) | 无                 |
| 3 | 即时放行入口(改造 2) | 核验页检索 + override + 重认证 | 小(能力已有,补入口)        | 与在途申诉通道同域,建议在其之上做 |

**风险排序**:改造 1 唯一有「行为回归」风险(外置后放行结果可能与原来不等价),**必须配等价性单测再合**;改造 2/3 纯增量、无回归面。

**与在途改动的关系**:改造 2、3 都落在「学号核验 / 反馈」域,当前工作区那批未提交的申诉通道改动(`FeedbackServiceImpl`、`AdminFeedback.vue` 等)就在这个域。**先别动工作区,等那批决定去留/提交后,再在这基础上叠改造 2/3**,避免交叉。改造 1 独立于申诉通道,可先行。
