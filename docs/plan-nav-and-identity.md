## 1. 设计不变量（最重要的一条）

> **不要引入任何"只需一个学号就能完成注册或认证"的自动化。**

这是用户明确的设计意图：六层校验的目的正是拦住"只知道某个学号、但不知道专业码与学号命名规则"的人。任何自动推导学校信息的能力，都会把这条防线拆掉（§2.2）。

后续任何人做优化时，若提出"简化注册流程""用学号自动填信息"，应先回看这一条。

## 2. 方案 B（已重做）：保留手填 + 认证后锁定

### 2.1 关键事实

- `CampusVerifyServiceImpl.saveSchoolProfile`：用户**手填** 学院/年级/专业。
- `submitStudentNo`：**先要求填完**（否则 `SCHOOL_PROFILE_INCOMPLETE`），再用 `validateStudentNoAgainstProfile` 六层硬校验：纯数字 / 长度(13-14) / 学号前2位==年级入学年份 / 层次标记==本专科 / 学号位3-8==专业code / 班内序号<70。
- `StudentNoAutoPassSupport.canAutoPass`：格式 + 院系与专业大类交叉校验都过 → `approveVerify` 直接置 `verify_status=1`，无人工。

**这套机制是有效的**，它拦住的是"只有学号"的人（§3.1）。

### 2.2 为什么取消「派生」——一个必须记住的相互作用

派生 = 由学号按编码规则算出专业/年级/学院，用户只填学号。

**它会让六层校验完全失效**：

- 派生后，专业/年级/学院是**系统从学号算出来**的，而六层校验比对的正是"学号 ↔ 专业/年级"。
- 两边同源 → 校验恒真 → 六层退化为空转。
- 更致命的是：攻击者**不需要懂任何规则**，只要填一个学号，系统自动把专业填对，六层必过、自动通过直接生效。
- 即用户所说：**"如果有派生的话只需要一个学号就可以注册。"**

手填不只是冗余，它**本身就是那道防线**——它强制申请人暴露"是否真懂这个学号"。派生把这个成本降到零。

**结论：撤销原方案 B 的派生部分，保留手填。**

### 2.3 保留的部分：认证后锁定（理由是数据一致性，不是安全）

已认证用户若能随意修改专业/学院，会破坏两件事：

1. **认证前提被打破**：「这些信息与我的学号一致」是认证时成立的事实，认证后随手可改，这个事实就不再成立。
2. **匹配失真**：同院系 / 同年级匹配（AC-14）直接读 `deptId` / `gradeId` / `majorId`，改错会让推荐给错人。

**做法**：

- `verify_status=1` 后，`SettingsProfile` 的学校信息段**只读**。
- 提供「重新认证」入口（决策 6）：用于转专业等学籍异动，由**管理员人工修正**（无名册下无法自动，见 §3.2）。
- 未认证前学校信息可自由编辑（这是六层校验能生效的前提）。

### 2.4 不再需要的后端改动（原方案 B 全部作废）

- ❌ `DictService.findMajorByCode` / `findGradeByEnrollYear`
- ❌ `StudentNoIdentitySupport.derive`
- ❌ `submitStudentNo` 改为"先派生"
- ❌ `StudentNoChangeSupport.apply` 同步重派生
- ❌ 精简六层校验

**六层校验一层都不动**，它现在是主力防线。

### 2.5 前端改动（缩减后）

| 文件                    | 改动                             |
| --------------------- | ------------------------------ |
| `SettingsProfile.vue` | 认证后学校信息段只读 + 「重新认证」入口；未认证保持可编辑 |
| `Settings.vue`        | 删「友声号」叫法                       |

## 3. 安全：真实威胁模型（已按用户反馈重算）

### 3.1 威胁分级——六层校验对谁有效

| 攻击者能力                | 六层校验     | 说明                                                |
| -------------------- | -------- | ------------------------------------------------- |
| 只拿到一个学号（照片、群聊、截图、捡到） | **有效拦截** | 不知道专业码、不知道命名规则，反推填不出来；这就是设计意图                     |
| 知道专业码对应哪个专业          | 部分拦截     | 仍需知道该专业属于哪个学院（`MAJOR_CLASS_TO_DEPTS` 16 条）才能过自动通过 |
| **知道全部命名规则 + 能查字典**  | **可冒充**  | 反推填一遍即可，且可能自动通过                                   |

所以之前文档里"认证挡不住任何冒充"的说法**过于绝对**，已修正：它对**最常见的攻击者（只有学号）是有效的**，这是真实且值得保留的防线。

残余风险 = "知道规则的人"。在**无名册 + 无校园邮箱**的前提下，这个风险无法消除，只能靠事后发现与下线（§3.4）。

### 3.1.5 ★ 六层的报错文案本身在泄露规则（不改则防线等于没有）

`validateStudentNoAgainstProfile` 抛出的业务错误，**每一条都在教攻击者学号命名规则**：

| 报错文案                            | 直接泄露了什么          |
| ------------------------------- | ---------------- |
| 「学号长度须为 13 或 14 位」              | 位数规则             |
| 「学号前两位与所选年级不一致」                 | **位 1-2 = 入学年份** |
| 「学号层次标记无法识别（应为本科 05/5、专科 06/6）」 | **层次标记的确切取值**    |
| 「学号专业编码与所选专业不一致」                | **位 3-8 = 专业编码** |
| 「学号班内序号不能大于 69」                 | **末两位取值范围**      |

**攻击路径**：拿到一个学号 → 随便填 → 逐条报错 → 五次之内把完整编码规则复原 → 反推填对 → 通过。

也就是说：**只要仓库不是私有，六层挡不住任何人**；而即使仓库私有，**报错文案又把它讲了一遍**。两份渠道合起来，规则等于公开。

**必须做的修改**：

1. 核对失败**不回传具体原因**，统一为模糊文案（如「提交成功，后台核对中」）。
2. 失败详情只写 `audit_log`，进管理员学号核对队列由人工看。
3. `STUDENT_NO_EXISTS` 同样模糊化（学号 13-14 位，遍历成本极低，明确报错=可批量扫出全校在册学号）。

这条与决策「注册成功 ≠ 认证成功」天然一致：**用户看不到失败，就学不到规则。**

### 3.2 一个必须确认的运维问题：仓库是否公开

六层校验的规则、`MAJOR_CLASS_TO_DEPTS` 映射、以及 `scripts/verify-studentno-parse.py`（里面把学号编码结构写得很清楚）**都在仓库里**。

- 若 GitHub / Gitee 是**公开**仓库 → 这些等于已公开，六层只防非技术攻击者，能力显著下降。
- 若**私有** → 规则未公开，防线上抬。

建议：确认后决定是否转私有。**这不影响本方案的其他部分**，但影响对残余风险的评估。

### 3.3 「友声号」删掉 + 学号脱敏收紧

它就是 `studentNo` 改了个名字，而学号同时是登录用户名（`AuthServiceImpl:146`）。

更实际的是脱敏形态：`UserVoAssembler.maskUsername` 对 13-14 位数字输出 `2308****0678`，**首尾各留 4 位**。学号结构是「入学年份(2) + 专业大类(4) + 专业位(2) + 班级(2) + 流水(2..4)」，脱敏后仍泄露**入学年份、专业大类、班级**——正好够外人去反推填表。

**动作**：

1. 删「友声号」叫法。
2. 公开面不再展示学号（`maskUsername` 对学号收紧，不留首 4 尾 4；或整体不展示，仅自己可见）。
3. 抽屉头部去掉「学号:xxx」那一行。

### 3.4 无名册 + 无校园邮箱 → 只能事后确证

既然无法事前确证身份，策略转向：①抬高伪造成本 ②给真用户快速翻案通道 ③出事能快速下线。

| # | 措施             | 做法                                                                                       | 优先级 |
| - | -------------- | ---------------------------------------------------------------------------------------- | --- |
| 1 | **学号脱敏收紧**     | 见 §3.3                                                                                   | 高   |
| 2 | **注册错误模糊化**    | `STUDENT_NO_EXISTS` 不再区分"已存在"与"格式非法"。学号 13-14 位，遍历成本极低，明确报错等于提供**枚举 oracle**，可批量扫出全校在册学号 | 高   |
| 3 | **申诉通道**（决策 8） | 六层校验失败时给出「我确实是本校学生，但学号校验没通过」入口，生成待管理员处理事项。真实同学被规则误挡时能自救                                  | 高   |
| 4 | **频率限制**       | 注册 / 认证提交按 IP + 设备限流，挡住批量注册与枚举                                                           | 高   |
| 5 | **被占号解绑**      | 管理员可释放冒用者占用的学号，让号回到本人手里（解决占号型拒绝服务）                                                       | 中   |
| 6 | **冒用举报**       | 个人主页加"举报此账号冒用我的学号"。**真实同学是最大的举报动机来源**，这是无名册下最关键的一条                                       | 中   |
| 7 | 校园邮箱路径         | **作废**（决策 2）                                                                             | —   |
| 8 | 自动通过           | **保留**。有手填兜底后它不再危险（只在申请人自填院系与学号专业大类一致时才触发，这本身需要知识）。不需要关闭                                 | —   |

### 3.5 已知代价

- **转专业但学号不变**：六层校验会因"学号专业 ≠ 实际专业"而拒绝，而无名册无法自动纠正 → 「重新认证」是**人工修正**，量级需要评估。
- **重名**：姓名仅作人工参考、不做匹配，故不构成误判（决策 3 已确认）。
- **知道规则的攻击者**：无法消除，只能靠 §3.4 的快速发现 + 下线。

## 5. 更多建议

### 5.1 同班同学

学号里 **`class_no`（位 9-10，班级号）** 目前只用于展示，没被利用。`专业code + 班级号` 已能唯一定位一个班。

校园社交里"找同班"是最自然的连接点，对内向用户尤其友好（不用搭话就有共同话题）。可作为「发现」里的一个维度。

注意：**这是匹配维度，不是认证依据**——它增加的是"找到同班"的便利，不改变认证强度。

### 5.2 字典运营化

- `MAJOR_CLASS_TO_DEPTS` 硬编码在 Java 里（新增专业要发版），下沉到字典表或配置。
- **未收录埋点**：六层校验失败时记录学号，运营看报表发现"哪些真实学号被规则挡了"——这正是决策 8 的申诉通道要处理的问题，数据化后可批量修规则。

### 5.3 导航延伸

- 意见反馈红点（type=11 未读计数）。
- 「我的反馈」直达（`FeedbackDialog` 暴露 `open(tab)`）。

### 5.4 增长

- **邀请同学**：同校/同班一键邀请（分享卡片 + 落地页）。校园推广期性价比高，但属独立工作量。
- **分享个人主页/帖子**：成本低，可后置。

### 5.5 工程

- 前后端都要过 `pre-push` 门禁；python 门禁（openapi/contract）本机才跑得动，改契约后先本地 `npm run check:all` 再推。
- 注意 `FeedbackDialog.vue` 已 297 行，新增文件别越 300。

## 7. 仍需确认

1. **仓库是否公开**（§3.2）——影响残余风险评估，若公开建议转私有。
2. **申诉通道落点**：复用现有反馈模块（低成本，管理员在一个队列处理），还是给学号申诉单开一条线（更清晰，多一点工作量）。
3. **「重新认证」的人工成本**：转专业学生量级多大？若多，考虑让管理员直接改专业而非整条重认证。
4. **是否接受"事后确证"**：承认注册无法完全确证身份，用快速举报 + 下线兜底。这是价值观取舍，需明确拍板。
